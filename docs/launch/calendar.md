# Seven-day distribution calendar

Day 1 begins only when the public release, installation links, and reporting
routes work. The schedule is a sequence, not a posting quota: skip channels
where current promotion rules disallow the content or where the audience is
already seeing the same launch. Check rules again on each posting day. Never
request coordinated upvotes, comments, or stars.

| Day | Channel and action | Specific CTA | Metric to record manually |
| --- | --- | --- | --- |
| 1 | GitHub: verify README, downloads, reporting routes, metadata; publish the two seed drafts after duplicate checks | Install and complete one shell detach → preview → attach loop | Voluntary successful-install reports and distinct installation blockers |
| 2 | Show HN: submit the repository with the prepared title and explanatory comment; stay available for questions | Try the loop; describe the step that did not work | Substantive workflow reports, split into reproducible issues and open questions |
| 3 | X: post the four-part thread and answer replies without recruiting engagement on HN | Try a shell session and report friction in Discussions | Distinct first-run reports received through the thread |
| 4 | One relevant Reddit community: re-check its rules and use the appropriate variant or permitted showcase thread | Explain how this compares with your existing tmux workflow | Concrete workflow objections and useful alternatives suggested |
| 5 | LinkedIn: share the practical workflow and current constraints | Try the return-to-session flow and identify unclear documentation | Actionable onboarding suggestions, not impressions alone |
| 6 | One Discord project-sharing channel where this is permitted; avoid duplicate audiences | Share one installation or session-discovery problem | Distinct support questions resolved or converted into reproducible issues |
| 7 | GitHub Discussions: write an evidence-based week-one recap and update issue links; reply in original threads only with relevant follow-up | Re-test an addressed issue or pick a scoped contribution | Resolved versus open reported blockers, plus accepted contributions |

Use [post copy](posts.md) and [seed drafts](seed-issues.md). A zero-response
day is a result; do not manufacture a recap, testimonial, or adoption count.
Only claim a fix after it has shipped or clearly identify an unreleased branch.

## Measurement without adding tracking to Atlas

Maintain a private launch log with date, channel, post URL, question/issue
link, outcome, and next action. Count a person only once per metric when the
same report appears in multiple channels. Do not copy sensitive support data
into the log. Ask about the source channel only when useful and voluntary.

GitHub traffic and release asset download counts can provide context when
available; neither proves an install, unique user, or successful session.
Record counts with the observation time. Atlas does not need telemetry for
this launch. Treat voluntary successful loops and reproducible friction as
the primary signals, and raw reach as context. No numeric growth target or
conversion claim is assumed.
